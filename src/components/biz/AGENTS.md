# Business management (biz) rules
- Personnel writes synchronize through biz_org_save/biz_appointment_save under biz_org_structure; private legacy writers retain guards. biz_member_affiliations holds secondary/scheduled affiliations, never duplicate primary personal obligations; appointment bindings fence visibility by dates. Title display sorts effective snapshots by rank/start/id and never grants actions. No bulk appointment backfill.
- Business: scoped biz_* RPCs, serialized organization/transfers, immutable content/workflow snapshots, final-official fences and audited Super Admin intervention; plans never enter approvals. Catalog appointments coexist with effective legacy managers under shared interval guards; biz_can and biz_scope_ok replace manual Role scope ceilings, with explicit audited exceptions. Titles never grant actions. Monthly source/one version, exact strings/NULL, frozen first deadline, VN time and user-keyed caches preserve history. No demo mode: dashboards read operational data only and show empty states.
- Biz Dashboard hierarchy (Toàn Khối→Hệ→Phòng→Nhóm→NV) aggregates server-scoped enriched facts client-side in src/lib/biz/hierarchy.ts mirroring biz_dashboard_aggregate; KRs merge only by Admin-set biz_kr_metrics.standard_code plus identical unit/kind/aggregation/direction, never by name — keeps scope server-side and prevents false merges.
- Reports: first submission is official instantly (biz_document_save sets approved + official_version_id, no approval run, no notification); only later adjustments (biz_document_start with mandatory reason) enter workflows, carry previous_items in the snapshot, and never replace official figures until decided. Attachments are optional https link JSONB (max 10, regex is portable — no bounded repetition); plans still require a Google Docs link on submit.
- Plan editors keep official URL state separate from attachments; planSubmission mirrors submit/draft validation and server milestone gates, normalizes RPC errors, and hides viewer tracking before a valid submitted version — prevents empty URL payloads and misleading states.
- Plans page (BizPlans.tsx) splits "Kế hoạch của tôi" / "Kế hoạch trong phạm vi quản lý" auto-shown by scope; view tracking lives in biz_document_views (per version × viewer) via biz_document_open RPC — never a shared is_viewed flag, never recorded on list/dialog views, only on explicit document open. my_view (none/unopened/opened/new_version) comes from biz_documents_read; biz_plans_unviewed feeds the Dashboard "Kế hoạch chưa mở của tôi" card.
- Plans and Reports share the "Công việc của tôi" section (BizMyWork.tsx) fed by read-only RPC biz_my_work(kind): it auto-lists open/overdue/next periods plus stale changes/pending late requests, never creates drafts, and skips periods where the user has no department (biz_period_department NULL) and no document — personal obligations must not depend on the management filter. Action buttons follow biz_deadline_phase (open→submit, overdue→late request flow, closed→read-only).
- KR goals page (BizGoals.tsx) uses the same personal-above/management-below layout (no tabs): read-only Year×Quarter summary first, 12-month detail and the input form open only on demand, drafts panel collapsed by default. Draft deletion goes only through biz_goal_draft_delete (owner with biz.goal_submit or Super Admin; draft status, never submitted, no approval run, not official; deletes the empty annual goal row, keeps the official version when removing an adjustment draft). biz_goal_start returns the existing open version, so duplicate drafts cannot be created by repeated saves or tabs.
- Deadline config is 3 milestones per kind (open/due/late_close, month offset -1..12, per-period exceptions) in biz_deadline_config; biz_deadline_at stays the due milestone for frozen history. First submissions are gated server-side by biz_deadline_phase (not_open/closed block, overdue needs an approved one-shot biz_late_requests row marked used atomically, Super Admin bypass is audited); resubmits after revision requests are never gated. Auto phase notifications ride the 5-minute wf/recover-cron pulse via biz_deadline_auto_notify (service_role only, dedup_key idempotent); config changes append to biz_deadline_config_log.
- Cài đặt không còn tab Phòng ban: Phòng/Nhóm/nhân sự/Trưởng Phòng quản lý duy nhất tại Cơ cấu tổ chức (biz_org_save/biz_appointment_save). Nguồn chính thức của Trưởng Phòng là biz_management_assignments/biz_appointments qua biz_scope_ok/biz_resolve_position; biz_department_members.is_manager chỉ là fallback legacy cho phòng chưa ánh xạ Hệ và biz_member_save từ chối ghi is_manager=true — tránh hai nơi hiển thị quản lý khác nhau.
- Biz: biz_can enforces appointment scope; null-system executives, trusted Admin, no deputy override; replacements retire old rights atomically. Since 0185, biz.*/k3.* permissions come ONLY from org appointments/exceptions or Admin/Super Admin — general Roles (app_roles.permissions, biz_detail_exception, sig_can) never grant business access; biz_participant/biz_all_scope/biz_can/k3_can and all biz RPC guards ignore them, and the general Role editor hides both groups. Published RPC uses private official/semantic aggregate helpers and shared charts, never grants detail access; goal/report decisions invalidate its cache. History/modules unchanged.
- Biz reset: biz_reset_preview/biz_reset_execute (Super Admin only, confirm string, backup in private.biz_reset_backups) clear business records only — plans, reports, user KR goals, late requests, approval runs and their notifications; org structure, positions, appointments, roles, KR catalog, deadlines, workflows and biz_deadline notifications are never touched. Execution always requires explicit in-UI confirmation; never run via tooling on shared data.
- Report settings live in the Reports page and reuse biz_report_cycle_* and biz_deadline_*; reportAllocations mirrors exact segment sums, and all first submissions recheck server deadlines before freezing timestamps — prevents duplicate configuration and client-only deadline bypasses.
- Report aggregation always resolves official_version_id, including legacy provisional callers; report duties use whole-period cycle matching and primary affiliation with existing-document preservation, while report activation requires all three ordered milestones — prevents pending adjustments, transition duplicates and incomplete schedules from altering operational totals.
- Rolling monthly plans use separate biz_rolling_plans/events and the existing goal_year approval engine with entity=rolling_plan; annual official_version_id is never replaced. Server validation locks past/current months, checks complete official monthly sources and snapshot identities at approval, and uses exact integer allocations — preserves annual commitments and historical evaluation. Ordinary approval steps only; legacy override rejects rolling entities until a scoped source-fenced intervention exists.
- Month completeness is decided only by private.biz_report_month_coverage (full/partial/none/na + missing obligations); never treat missing reports as zero. Opening balances live in biz_opening_actuals via biz_opening_actual_save (privileged, mandatory source note, event history, no auto-zero, no double counting with official reports); rolling basis and report actual ranges consume coverage — change them together.
- Default workflow templates come only from biz_workflow_seed_defaults (5 groups × per system, idempotent, position-based steps, inactive "Cần hoàn thiện" when a position has no holder, never overwrites existing workflows); biz_workflow_simulate previews the resolved chain. Concurrent report/opening writes use per-user advisory locks (0170) instead of table-wide biz_documents locks — keep both writers on the same lock key.
- Quản lý 3K is independent of KR/plans/reports/Dashboard. k3_can resolves existing permissions/appointments; cross-user day/period reads use frozen department attribution and biz_scope_ok at work time, never grant edits to managers. k3_tasks is the single task source; KG/KF store commitments only, is_unscheduled excludes actual/date totals until audited k3_task_schedule, deleted_at preserves comments/events. Owner advisory locks, request keys, revision fences, summary fingerprints and immutable snapshots protect writes/history; VN deadlines and KPI/VNGB checks remain authoritative in RPCs.
- Canonical measured KPI results use k3_kpi_results (one KPI/performer/date) with immutable result versions and day confirmations; all new result entry uses Biz3KKpiResult and k3_kpi_result_save. Legacy k3_tasks remain historical executions, never automatically guessed into measured KPI results. Private counted backups precede review archival; timed archival never purges official history.
- 3K auto-close uses SQL-only scheduled k3_auto_close_run and immutable k3_daily_closes; system confirmation is explicitly source=auto, never attributed to an employee. Post-close corrections require reasons and reconfirmation. Independent k3_zalo_reports snapshots are sent by the existing authenticated cron pulse with fenced non-reclaimable send claims; unknown delivery never replays and module configs never touch Finance/Leave groups.
- 3K UI has exactly three business tabs plus a separate settings button (Biz3K.tsx): "3K Của Tôi" (Biz3KGoals variant=personal + Ngày/Tuần/Tháng/Quý/Tất cả views), "3K Nhóm/Phòng Ban" (Biz3KGoals variant=collab — only KGs with invited/accepted members, never member monitoring), and "Theo Dõi Nhân Viên" (Biz3KManage + Biz3KPeriod manage, can_view_scope only) — never re-add standalone "KG tham gia"/"Trong phạm vi quản lý" tabs or merge monitoring into the collab tab. "Tạo công việc" always means creating a KG with KFs/KPIs via the atomic k3_quick_create RPC (Biz3KQuickCreate, request_key idempotent, start requires ≥1 KF); "Ghi nhận thực hiện" only logs daily execution onto an existing KF — never create parallel task-only records as the primary flow (legacy unlinked tasks stay editable). k3_team_read returns status_key (none/planned/updated/summarized/reconfirm) plus goals_active/kf_active/kf_overdue — never revive the "Chưa lập 3K" concept. Since 0194: k3_action_worker_ok and day-read/goal-list require accepted membership (revoke kills write+list access, history kept); custom KG date edits persist server-side; k3_tasks.kpi_id links each execution to one KPI (legacy NULL kpi_id still aggregates by unit, never double-counted); assigned_actions hide KF whose start_date is in the future.
